## 0. 接手前必讀的五條硬規則

1. **這個 repo 根目錄有兩個不同的遊戲。** 根目錄的 `index.html` 是另一款「天堂放置版」，
   與本專案無關。**本專案是 `天下無雙放置版/` 這個子資料夾**，所有工作都只能在這裡面進行。
2. **不要把「自研數值」說成「官方數據」。** 本文件第 5 節明列哪些是官方查證過的、
   哪些是自行設計的。這個區分是使用者反覆強調的要求。
3. **全部遊戲邏輯都在 `index.html` 的單一內嵌 `<script>` 裡**（約 1,690 行）。
   V1.0.7 曾拆成 `data/` 底下 32 個模組，**V1.0.8 又併回單一檔案**（使用者要求）。
   原模組邊界以 `/* ══ [n/32] data/檔名 ══ */` 標題註解保留，搜尋標題即可定位。
4. **`官網資料/` 裡的檔案是自動產生的，不要手改。** 改了會被重新產生覆蓋。
   要調整請改產生腳本，或改 `index.html` 內 `[ 6/32] data/config.js`、
   `[10/32] data/combat-model.js` 兩個區塊裡的參數。
5. **改版本號要同步改四個地方**（見第 7 節），且每一批更新版本號末碼 +1。

### 2.2 內嵌 script 的區塊順序（順序不可任意調換）

`index.html` 的內嵌 `<script>` 裡，32 個原模組依序排列，每段前面都有標題註解：

```js
/* ══════════════════ [ 1/32] data/official-data.js ══════════════════ */
```

順序如下（搜尋 `[ n/32]` 可快速跳到該段）：

```
 1 official-data      2 classes-skills    3 equip-db        4 dungeon-boss-db
 5 market-pet-quest   6 config            7 exp             8 state
 9 utils             10 combat-model     11 save           12 offline
13 player            14 stats            15 equipment      16 monster
17 combat            18 potion           19 drops          20 battle-flow
21 forge             22 inventory        23 shop           24 ui-core
25 ui-panels         26 inventory-ui     27 skills-ui      28 dungeons
29 ai-panel          30 system-ui        31 render-loop    32 boot
------- 以下是 index.html 之外的外部 script -------
warehouse.js         login-bgm.js        lobby.js
```

**順序規則（改動時務必遵守）**

| 規則 | 原因 |
|---|---|
| 1～5 的資料區塊必須最先 | 它們在「執行到當下」就運算：`SKILLS` 由 `SKILL_SEED` 產生、`EQUIP_DB = buildEquipDB()`、`BOSS_DB`、`MARKET`、`POOL_ITEMS` 都需要前面的常數 |
| `config` 在 `state` 之前 | `freshState()` 用到 `GAME_VERSION` |
| `state` 在所有功能區塊之前 | 它宣告 `let G = freshState()`，`G` 是整個遊戲的狀態物件 |
| `combat-model` 在 `stats`／`monster` 之前 | 那兩段會呼叫模型的函式 |
| `boot` 必須最後 | 綁按鈕、`normalize()` → `renderAll()` → 啟動 `mainLoop`，並用 `Object.assign(window,{…})` 把函式掛上 `window` |
| `login-bgm.js` 在 `lobby.js` 之前 | `lobby.js` 會呼叫 `window.TXWSLoginBGM.start()` / `.stop()` |

中段（13～32）幾乎都是 `function` 宣告（會被提升），彼此順序其實不影響，但請照表排。

> **併檔後多了一個風險**：以前是 32 個獨立 `<script>`，其中一個出錯不影響其他；
> 現在是單一 script，**任何一處語法錯誤會讓整個遊戲不執行**。改完務必跑第 7.2 節的檢查。

### 2.4 跨檔耦合（改動時容易踩到的）

- **全域變數串接**：傳統 script，沒有 `import/export`。靠全域 `G`、`battle`、
  `SKILLS`、`EQUIP_DB`、`maps`、`bossBase`、`OFFICIAL_MONSTER_DATA` 等互通。
- **`onclick="xxx()"` 只找得到 `window` 上的函式**。新增給 HTML 直接呼叫的函式時，
  必須加進 `[32/32] boot` 區塊最後的 `Object.assign(window, {...})`，否則按鈕點了沒反應。
- **`'use strict';` 只有一個**，寫在內嵌 script 的最開頭，整段都是嚴格模式。
  併檔時已把原本各模組自己的那一行移除，不要再往中間加。
- **`ensureStats()` 是數值總匯流點**：裝備、寶石、血珀、靈寵、天賦、精煉都在這裡加總。
  它被戰鬥迴圈高頻呼叫，不要在裡面做昂貴的運算。
- **存檔相容**：`normalize()` 用 `deepMerge(freshState(), G)`，新增欄位會自動補上，
  移除欄位則會殘留在舊存檔裡（無害）。`G.version` 只寫不讀，改版號不影響存檔。

## 4. 戰鬥數值模型（V1.0.8 已上線）

### 4.1 為什麼要做

校準實測發現現行數值在高等級完全崩潰：

| 等級 | 玩家幾下打死怪 | 怪物幾下打死玩家 |
|---|---|---|
| Lv10 | 7 | 18 |
| Lv40 | 26 | 6 |
| Lv65 | 71 | **2** |
| Lv90 | **165** | **1** |

成因：**玩家三圍成長是線性**（攻擊 91→1270、氣血 532→6696、防禦 40→1037，每級固定增量），
**怪物是冪次成長**，Lv40 之後兩條曲線迅速分離。

### 4.2 改了什麼

| 區塊 | 改動 |
|---|---|
| `[10/32] combat-model` | **新增的區塊**。四個模組的公式與參數集中於此，**每個數值都標註 `[官方]`／`[參照]`／`[自研]`** |
| `[14/32] stats` | `hitChance`、`critMultiplier`、`randomVariance`、`calcDamage`、`ensureStats` 改為委派給模型 |
| `[16/32] monster` | `monsterData()` 的 HP／攻／防改由模型推導；結構性欄位（等級／體型／種族／相性／五行／掉落）原封不動 |

**修正的三個缺陷：**

1. **防禦斷崖** —— 舊式 `攻擊×倍率 − 防禦×0.5`，攻擊低於防禦一半時傷害被 `max(1,…)` 壓成
   1 點。改為比例減傷 `K/(K+防禦)`（公式結構屬業界常見模型，K 值自研）。
2. **「準」完全失效** —— 舊式 `clamp(0.82 + accuracy − 閃避×0.45, 0.55, 0.995)`，
   其中 `accuracy` 本身已是 0.78～0.99，`0.82+0.78=1.60` 永遠超過上限，
   **命中率恆為 99.5%、準與閃避都無作用**。現在準 0→75%、準 20→93%。
3. **曲線分離** —— 怪物數值改由玩家基準線反推，全等級維持一致節奏。

**改動後實測（全表 36 隻怪）：** 打死怪中位 **12 下**、被打死中位 **19 下**
（設計目標 12／20），範圍 8～27 下。

### 4.3 三個設計取捨

- **保留怪物個性**：純用「等級＋體型＋種族」推導會讓樹魔與幻魔妖姬（同為 Lv60 中魔）
  數值完全相同（原本 12,000 vs 95,000）。改用現有手調表當「相對強度權重」，
  權重帶寬收窄到 1.7 倍以壓制極端值（沙鬼 Lv30 卻有 9,500 HP，是虎 Lv10 的 27 倍）。
- **新手保護曲線**：桃花林出 Lv4～8 的怪但玩家是 Lv1 且未配裝，照同級基準會變成
  「打死怪 21 下、被打死 12 下」，玩家不斷觸發自動撤退、永遠殺不死第一隻怪。
  Lv1～15 套用由 0.45 線性回升到 1.0 的係數。
- **五屬轉換係數維持原值**：它們是整個模型的錨（怪物數值由玩家曲線反推），
  改動會使怪物模型需重新校準。這次做的是集中、標註來源、可調化，並修好失效的「準」。

### 4.4 調校介面

```js
// index.html 內嵌 script 的 [10/32] combat-model 區塊
COMBAT_TARGET.killHits     // 玩家打死同級一般怪的普攻次數（現值 10，實測中位 12）
COMBAT_TARGET.surviveHits  // 同級一般怪打死玩家的次數（現值 20，實測中位 19）
DEF_K_PER_LEVEL / DEF_K_MIN // 防禦減傷的強度
HIT_BASE / HIT_MIN / HIT_MAX // 命中率上下限
MONSTER_ANCHORS = {}       // 【預留】填入 {'怪物名':{hp,atk,def}} 可直接覆蓋個別怪物
EARLY_LEVEL / EARLY_MIN    // 新手保護曲線
```

> 使用者表示會另外提供一份「怪物 HP 錨點表」。收到後填進 `MONSTER_ANCHORS` 即可，
> 不需要改任何公式。

### 4.5 要退回舊的戰鬥數值

這批已在 V1.0.8 上線。若要退回 V1.0.7 的舊公式（不建議，舊公式有第 4.1 節的崩潰問題）：

**注意**：舊版 `calcDamage` 用減法防禦、`hitChance` 的「準」無效，退回等於把三個已修好的缺陷放回去。

### 🟢 P2 — 已釐清但需要決策

**P2-1：官方招式倍率與本遊戲普攻不同量級**（實測過的真實問題）

Lv30 角色配青鋒劍（baseAtk 142）時：

| 攻擊方式 | 傷害 | 算法 |
|---|---|---|
| 普攻 | **642** | 角色總攻擊力 × 1.0 |
| 法術·擊 | 189 | 人物狠 × 100%（官方） |
| 劍道·松 | **19** | 武器狠 × 10%（官方） |

官方公式沒抄錯（用官方等值武器 狠+120 驗算，松 Lv1 算出 12，與官網完全一致）。
問題在於**兩套公式基數不同**：官方招式只吃「武器威力」，本遊戲普攻吃「角色總攻擊力」。
低階招式（×10%～20%）照官方算必然遠弱於普攻。

三個方向：(a) 普攻也改吃武器威力（最忠於官方，但普攻大幅削弱）；
(b) 招式基數改為「武器威力＋角色攻擊力的一部分」；(c) 官方倍率只用在高階招式。

**P2-2：`EQUIP_NAMES` 漏掉 13 件基礎裝備（既有 bug，交接時發現）**

`[ 3/32] equip-db` 區塊的執行順序有問題：

```js
L36  const EQUIP_DB = buildEquipDB();        // 75 筆
L37  const EQUIP_NAMES = Object.keys(EQUIP_DB);   // ← 在這裡就定案了，只有 75 筆
L39  const BASIC_EQUIP = { … };              // 13 件基礎裝備
L54  Object.assign(EQUIP_DB, BASIC_EQUIP);   // ← 這時才併進來，EQUIP_NAMES 沒跟著更新
```

結果：`EQUIP_DB` 有 88 筆，但 `EQUIP_NAMES` 只有 75 筆，**13 件基礎裝備不在名單裡**。
用 `EQUIP_DB[名稱]` 查詢正常，但凡是遍歷 `EQUIP_NAMES` 的功能都看不到基礎裝備。

受影響的使用者：`[23/32] shop`（商店清單）、`[25/32] ui-panels` 的 `classAiName()`
（AI 配裝建議）、`[21/32] forge`。

修法：把 L37 移到 L54 之後，或改成 `const EQUIP_NAMES = Object.keys(EQUIP_DB)` 於合併後執行。
**注意**：修好之後基礎裝備會開始出現在商店與 AI 建議清單中，是行為變更，
請確認這是期望的結果（也可能當初就是刻意不讓基礎裝備進商店）。

**P2-3：官方「武器狠」的對應關係（已釐清，可直接沿用）**

官方寫「傷害為武器狠×N%」，這個「武器狠」指**武器攻擊力本身**
（官網 40 級蕩邪劍＝狠+120、除魔貫＝狠+133），對應本遊戲武器的 `baseAtk`
（青鋒劍 142），**不是** `attr.狠`（只有 8）。
接官方倍率時 `officialWeaponAttr()` 必須把 `baseAtk` 算進 狠／智，否則會算出個位數傷害。

## 7. 專案慣例

### 7.1 版本號規則

**每一批更新版本號末碼 +1**（V1.0.6 → V1.0.7 → V1.0.8）。已推送的版本不回頭改。

改版本號要同步改**四個地方**：
1. `index.html` 內 `[ 6/32] config` 區塊的 `const GAME_VERSION='v1.0.x';`（登入頁版號自動讀這個）
2. `index.html` 更新選單的標題「天下無雙・放置版 V1.0.x」與「目前版本：V1.0.x」，
   並把更新選單內容換成該版重點
3. `index.html` 內 `[30/32] system-ui` 區塊，設定頁底部的 `<p class="footer-note">V1.0.x · …`
4. `README.md` 最上方標題，並在版本表新增一列

### 7.2 驗證流程（每次改完都要跑）

```bash
# 1. 語法檢查全部模組
for f in 天下無雙放置版/data/*.js; do node --check "$f"; done

# 2. 起本機伺服器實跑（不能用 file:// 開，CSS mask 會因 CORS 失效）
python -m http.server 5199 --directory 天下無雙放置版
```
然後在瀏覽器確認：登入畫面 → 點擊 → 選角 → 創角 → 進入遊戲 → 掛機能擊殺升級，
且 **console 零錯誤**。改到戰鬥公式時，另外確認低等級（Lv1 未配裝）與
高等級（Lv90）兩端都不會失衡。

### 7.3 踩過的坑

| 坑 | 說明 |
|---|---|
| **瀏覽器快取** | 改完 `index.html` 後重新整理常常還是舊的。最可靠的是在網址後面加查詢字串，例如 `index.html?nocache=1`；開新分頁次之，`location.reload()` 最不可靠 |
| **PowerShell 變數不分大小寫** | `$slot` 會覆蓋 `$SLOT`。寫轉換腳本時對照表一律用 `_MAP` 結尾命名 |
| **`ConvertTo-Json` (PS 5.1)** | 會把巢狀陣列包成 `{"value":[…],"Count":n}`，陣列要自己序列化 |
| **PowerShell 字串插值** | `"$setName套裝"` 會被當成變數名 `$setName套裝`（中文字是合法變數名），要寫 `"${setName}套裝"` |
| **`file://` 開不了** | `ui-icon-masks.css` 的遮罩雖然內嵌了，但整體仍建議用本機伺服器測試 |
